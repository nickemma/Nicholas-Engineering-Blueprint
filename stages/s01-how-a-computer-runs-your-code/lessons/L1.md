## Part 1 — Understanding Programs and Processes
A file is just bytes

### What a program actually is: **A program is a file. A process is a running instance of it.**

e.g.,
hello.go = text file containing Go code 80 bytes

↓

go build hello.go = translates hello.go to a machine code file hello.exe (or hello on Linux)

↓

hello on disk, does nothing until it is executed

↓

./hello = runs the program, kernel loads it into memory, creates a process, and executes it

↓

a process is a running instance of a program, with its own memory space, file descriptors, and execution context.(PID, memory, open files, exit code)

## Part 2 — The mental model
Hold this one. It'll carry you a long way.

**A program is a recipe. A process is a cook, in a kitchen, cooking it.**

e.g., hello.go The recipe is a page in a cookbook, it doesn't do anything.

To cook, you need a kitchen:counter space(memory), ingredients (input), a bin (output), a timer (CPU), and a cook (process) to follow the recipe.

The OS is the restaurant manager, who assigns you a kitchen, hands you the recipe, and lets you cook. 

Three cooks can cook the same recipe at the same time in three kitchens, same recipe, three completely independent processes(cooks). If one sets the kitchen on fire, the other two are unaffected.

#### Now stretch the model a little, because it explains things you'll hit later today:

* You can burn the recipe after the cook has read it. Delete the source, the process keeps going.
* The cook doesn't need the recipe book once they've memorised it. The machine code was copied into memory; the file on disk is no longer in the loop.
* The manager decides which kitchen you get, and you can't wander into someone else's. That's memory protection.

## Part 3 — The real terminology
Now the words. Each one attaches to something you already understand from above.

Term | What it actually is
--- | ---
Source code | Your text file. `main.go`. Human-readable, machine-useless.
Compiler | The translator. `go build` is one.
Machine code | The numbered instructions a specific CPU family understands.
Binary / executable | The file containing machine code, marked as runnable. `main.exe` or `main`.
ELF | The file format Linux executables use. Like .png is a format for images. First four bytes of every one: 7f 45 4c 46 — that's \x7f then the letters E, L, F. You'll see it today.
Kernel | The core of the operating system. The part that owns the hardware and hands out kitchens.
Loader | The kernel's component that reads a binary and sets up its memory.
Process | A running instance: the code, its memory, its open files, its identity.
PID | Process ID. The number the OS uses to refer to it.
Entry point | The address of the first instruction executed. Not `main()` — Go's runtime starts first and calls your `main` later.
File descriptor | A number the OS uses to refer to an open file. 0 = stdin, 1 = stdout, 2 = stderr. You can open more files and get more numbers.
Exit code | A number a process returns when it dies. 0 means success. Anything else means something specific to that program.
Environment | A set of `key-value` pairs the OS gives a process at birth when it starts. `PATH` is one of them.

One correction to a thing almost everyone believes: `main()` is not where your program starts. The kernel jumps to an entry point that belongs to the Go runtime. The runtime sets up the scheduler, the garbage collector, and the memory allocator — then calls your `main`. By the time your first line runs, thousands of instructions have already executed.


## Part 4 — The tiny example
Make a folder and put this in hello.go:
```go
package main

import "fmt"

func main() {
	fmt.Println("hello")
}
```

Six lines. Now:
```bash
go build -o hello hello.go
./hello
```
`hello` printed. what you should notice:
* go build produced a new file called. That file did not exist before. Something was created, not just interpreted.
* The build took a moment. Translation is real work.
* `./hello` needed the `./`. That's you telling the shell "the file is right here, not somewhere in the system's list of program locations."
* Nothing printed until you ran it. The binary sat there inert.


## Part 5 — Experiments — your turn
Run every one of these. Don't read them and nod. The whole point of an EXPERIMENT lesson is that you watch it on your own machine. Commands assume Linux (WSL counts).

#### E1 — How big is six lines?
```bash
wc -c hello.go: (66 hello.go)
ls -l hello.go: (2.3M)
```
Your source is roughly 80 bytes. Your binary is over a megabyte. Write down both numbers.

##### Ask yourself before reading on: where did a million bytes come from?
**The answer: the Go runtime got baked in. Garbage collector, scheduler, memory allocator, stack management — all of it is compiled into every Go binary. That's why a Go program can be copied to a bare Linux machine with nothing installed and just work. It's carrying its whole world with it. That is a tradeoff: big files, zero dependencies.**

#### E2 — Look at the bytes
```bash
xxd hello | head -3
file hello
```
The first four bytes are 7f 45 4c 46. That's the ELF magic number — how the kernel knows this file claims to be an executable. file reads those same bytes and tells you in English.

#### E3 — Exit codes
```bash
./hello
echo $?
```
0. Now change the program:

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	fmt.Println("hello")
	os.Exit(3)
}
```

```bash
go build -o hello hello.go
./hello
echo $?
```

3. You just process report something to whoever started it. This is how every script, CI pipeline, and process supervisor on earth decides whether something worked.

#### E4 — Watch a process actually exist
Processes normally live for microseconds, too fast to observe. So make one that lingers:
```go
package main

import (
	"fmt"
	"time"
)

func main() {
	fmt.Println("sleeping")
	time.Sleep(120 * time.Second)
}
```

```bash
go build -o sleeper sleeper.go
./sleeper &
```

The & runs it in the background. Now:
```bash
pgrep sleeper
ps -p $(pgrep sleeper) -o pid,ppid,stat,rss,cmd
```
You now have a PID. 303660

#### E5 — Open the process and look inside it
This is the most important experiment in the lesson. On Linux, every running process is exposed as a directory. Replace <PID> with your number:
```bash
ls /proc/<PID>/
cat /proc/<PID>/cmdline | tr '\0' ' '; echo
cat /proc/<PID>/environ | tr '\0' '\n' | head
ls -l /proc/<PID>/fd/
grep -E 'VmRSS|State|Threads' /proc/<PID>/status
```
Read what came back slowly:

* cmdline — the exact command that started it. The OS kept a copy.
* environ — every environment variable, handed over at birth and frozen there.
* fd/ — the open channels. You'll see 0, 1, 2 pointing at your terminal. Those three are the stdin/stdout/stderr from the table above, and now they're not an abstraction, they're directory entries you just listed.
* VmRSS — how much physical memory it's actually using.
* Threads — more than 1, even though you wrote no concurrent code. That's the Go runtime.

You are looking directly at the kitchen the OS built. Everything in Part 1 is now visible.

#### E6 — One program, three processes
```bash
./sleeper & ./sleeper & ./sleeper &
pgrep sleeper
```
Three PIDs. One file on disk. Three independent lives.

```bash
kill <one of them>
pgrep sleeper
```
Two survive. This is the program/process distinction made concrete, and it's the single idea from today you'll use most often.

```bash
pkill sleeper
```

## Part 6 — Now we break it
Four deliberate failures. For each: predict what will happen before you run it, write your prediction down, then run it. The gap between your prediction and reality is where learning lives.

B1 — Delete the source while it runs
```bash
./sleeper &
rm sleeper.go
``` 

Still running? Why?
B2 — Delete the binary while it runs
```bash
rm sleeper
pgrep sleeper
```
Still running. The file is gone from the directory listing — but the machine code was copied into memory at load time, and the kernel keeps a reference to the file's contents until the last user is finished with it. The name in the directory and the data are two different things. (Hold onto that. It comes back in Lesson 6, and it's the reason "the disk is full but I deleted the logs" is a real production incident.)

**Rebuild before continuing.**

B3 — Take away the executable bit
```bash
go build -o sleeper sleeper.go
chmod -x sleeper
./sleeper
```
Permission denied. The kernel won't even try to load it.
Now the question I actually want answered: not a single byte inside the file changed. So what did? What is the kernel checking, and where does that information live if not in the file's contents?

B4 — Build for the wrong machine
```bash
GOOS=windows GOARCH=amd64 go build -o hello.exe hello.go
file hello.exe
./hello.exe
```
Different format, and it won't run. The machine code inside is for a different operating system's conventions. This is the concrete proof of "different CPUs and different OSes eat different numbers" from Part 1.
